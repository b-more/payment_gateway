How the gateway API is built

A field guide for partner engineers integrating collections and disbursements over Zambian mobile money. Every call is individually signed, every amount is integer ngwee, and every transaction runs the same locked state machine. Here is exactly how it fits together.

Flow

A request's journey

Every /v1 call passes the same ordered pipeline before it reaches any business logic. This sequence is the contract — get through it and you're talking to the engine.

  1. nginx → API

    TLS terminates at the edge; the request is proxied to the service with its path and body preserved byte-for-byte.

  2. Raw-body capture

    The exact bytes of the body are kept as rawBody. The signature is computed over these bytes — re-serialised JSON would differ and break verification.

  3. Rate limit

    Per-credential throttling rejects abusive callers before any lookup work is done.

  4. Authenticate

    The signed request is verified (see below). On success a CredentialContext — key, account, environment — is attached to the request.

  5. Validate

    The body is validated against a strict schema. Unknown fields are rejected outright, not ignored.

  6. Handle

    The controller does the work, always scoped to the authenticated key's own account — a key can never see another merchant's data.

  7. Serialize & return

    Domain errors map to a clean { error: { code, message } } envelope; money serialises as integer-ngwee strings.

Auth

Two ways in — pick your level

Authentication is per-request, not per-session: nothing to expire or refresh. Start with key + secret; move to signing if you want the extra hardening.

✅ Simple — key + secret recommended

Send X-Api-Key + X-Api-Secret (or Authorization: Bearer <secret>) on every call. The familiar key-and-secret-over-TLS model — you can be live in minutes.

🔐 Signed — HMAC hardened

Don't send the secret at all — prove each call with a signature. Adds replay protection and body integrity. Send X-Signature and the API switches automatically.

How the server verifies a signed request — a fixed sequence:

  1. Resolve the key

    Look up the credential by X-Api-Key; reject immediately if it's missing or not active.

  2. Check the window

    Reject timestamps outside ±5 minutes — a captured request can't be replayed later.

  3. Recompute & compare

    Decrypt the signing key (stored encrypted, never plaintext), recompute the HMAC, and compare in constant time.

  4. Enforce IP allowlist

    For live keys only, the request IP must be on the account's allowlist — in both auth modes. Sandbox keys skip this.

reference client — key + secret (Node)
import crypto from 'node:crypto';

const API_BASE = 'https://api.instacompayzm.com';
const API_KEY = 'ic_live_…', API_SECRET = 'sk_…';

async function call(method, path, body) {
  const headers = {
    'Content-Type': 'application/json',
    'X-Api-Key': API_KEY,
    'X-Api-Secret': API_SECRET,
  };
  // any unique string — re-send the same one to safely retry
  if (method !== 'GET') headers['Idempotency-Key'] = crypto.randomUUID();

  const res = await fetch(API_BASE + path, {
    method, headers, body: body ? JSON.stringify(body) : undefined,
  });
  return res.json();
}

// K50.00 collection — amount is integer ngwee, as a string
await call('POST', '/v1/collections', {
  processor: 'AIRTEL', amount: '5000', msisdn: '260970000001',
  collectionReference: 'order-1001',
});
Money

Integer ngwee, always

The single most important data rule. There are no decimals and no JSON numbers anywhere in the money path.

Unit

1 Kwacha = 100 ngwee. K1.50 is sent as "150"; K50.00 as "5000".

Type

Strings on the wire, bigint internally. A float can't silently round a customer's money.

Enforced

Validated on input, stored as integers, and re-serialised to strings on output — end to end.

Engine

One transaction state machine

Collections and disbursements share a single entry point. It runs inside one database transaction with the account row locked, so concurrent calls can't race the float balance.

CREATED → PROCESSING →
SUCCESS FAILED
⇢ REVERSED

SUCCESS and FAILED are terminal; only a SUCCESS may later be REVERSED. Illegal jumps are rejected.

Debit, then dispatch

On a production transaction the engine loads the charge config, checks float, appends a DEBIT to the append-only float ledger, marks the transaction PROCESSING, then hands off to the rail.

Idempotent completion

A callback and a status-poll can both try to resolve the same transaction. The first wins; the rest are no-ops. A FAILED result appends a compensating refund so the ledger always balances.

Insufficient float

If the balance can't cover amount + charge, the transaction is written FAILED with INSUFFICIENT_FLOAT and nothing is debited.

Append-only ledger

Float entries are never updated or deleted — only appended. The ledger is a forensic record you can always reconcile against.

Rails

Dispatch, then three ways to resolve

Once a transaction is PROCESSING, the gateway pushes it to the mobile-money rail (Airtel / MTN), recording a per-attempt trail. It then settles by whichever of these fires first — all idempotent, so they never double-count.

① Rail callback

The processor calls a signed webhook endpoint the moment the customer approves or the transfer lands.

② Resolve-on-read

GET /v1/transactions/{id} re-enquires the rail live, so polling reflects the true state in real time.

③ Reconcile sweep

A guarded cron sweeps anything still in flight every few minutes — the backstop that guarantees eventual settlement.

↺

Because completion is idempotent, you can safely poll and rely on webhooks at the same time. Whichever arrives first settles the transaction; the other becomes a harmless no-op.

Safety

Idempotency on every write

Every mutating call carries an Idempotency-Key. It's what makes retries safe over flaky mobile networks.

Replays return the original

Re-send the same key and you get the original transaction back — no second charge, no second webhook, no second dispatch.

Race-safe

Two requests with the same key arriving at once resolve to a single transaction; the loser simply returns what the winner created.

🔐

Always verify the signature. Without it, anyone who learns your callback URL could POST a fake “payment received”. Reveal your secret (whsec_…) in the Merchant Portal → API Documentation, or via GET /v1/merchant/accounts/{id}/webhook-secret.

verifying a webhook (Node)
import crypto from 'node:crypto';

const WEBHOOK_SECRET = 'whsec_…';

// Verify against the RAW body bytes, before any JSON parsing.
function verify(rawBody, header) {
  const p = Object.fromEntries(header.split(',').map((x) => x.split('=')));
  const expected = crypto.createHmac('sha256', WEBHOOK_SECRET)
    .update(`${p.t}.${rawBody}`).digest('hex');
  const a = Buffer.from(expected), b = Buffer.from(p.v1 ?? '');
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}

app.post('/webhooks/instacompay', (req, res) => {
  if (!verify(req.rawBody, req.get('X-Instacompay-Signature'))) {
    return res.sendStatus(400);        // forged or tampered
  }
  // mark the order paid — idempotently, we may retry
  res.sendStatus(200);
});

Env

Sandbox and production

The same code path, branched on the key's environment. Build and test against sandbox with zero risk, then swap one key to go live.

🧪 Sandbox  ic_sand_…

Sandbox simulates and settles instantly, so you can exercise the real PROCESSING → SUCCESS lifecycle. Nothing touches a live rail, and it's fully isolated from production float — test all day without spending a ngwee.

🔟 Production  ic_live_…

Real rails, real float, real settlement. Live keys additionally enforce your IP allowlist. Money moves the moment the customer approves.

⚑

Start in sandbox. It resolves to SUCCESS immediately, so you can prove your whole integration — create, poll, handle the result — before switching a single key to live.

Recap

The whole model, in one line

sign every request → rate-limit + verify HMAC → validate → lock account & run the state machine (debit float → PROCESSING) → dispatch to the rail → resolve via callback / poll / reconcile → return money as integer-ngwee strings.
