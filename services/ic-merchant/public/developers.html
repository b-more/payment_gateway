The merchant portal, as an API

The endpoints behind merchants.instacompayzm.com — sign in with email + one-time code, then collect, track status, and run maker-checker payouts against your own accounts. This is the flow proven live end-to-end: a K1 Airtel collection went PROCESSING → SUCCESS on the first try.

Sign in

Session authentication

Unlike the public integration API (which signs every request), the portal uses an email one-time-code login and an httpOnly session cookie — the same login a person uses in the browser.

  1. Log in with email + password

    POST /v1/auth/merchant/login — verifies the password and emails a 6-digit code. Returns a challengeId.

  2. Verify the code

    POST /v1/auth/merchant/verify-otp with the challengeId and the emailed code. On success the response sets httpOnly session cookies and returns your user (id, email, roles).

  3. Call with the cookie

    Send the cookie on every request (credentials: 'include' in the browser). GET /v1/auth/merchant/me returns the current session; POST …/refresh rotates it; POST …/logout ends it.

🔒

The session is scoped to your merchant. Every endpoint below only ever sees your own accounts, transactions, and users — there is no way to reach another merchant's data.

Collect

Take a payment

Charge a customer's mobile-money wallet from one of your accounts. Amount is integer ngwee as a string — K1.00 = "100". A production collection sends a real prompt to the customer's phone.

POST/v1/merchant/accounts/{accountId}/collectcustomer → you
Request body
{
  "processor": "AIRTEL",
  "amount": "100",
  "msisdn": "260970000001",
  "reference": "order-1001"
}
Response · 200
{
  "id": "9893373a-…",
  "type": "COLLECTION",
  "processor": "AIRTEL",
  "amount": "100",
  "charge": "3",
  "net_amount": "100",
  "status": "PROCESSING"
}
📲

Production returns PROCESSING and prompts the customer — poll the status endpoint until it turns SUCCESS once they enter their PIN. Sandbox accounts simulate and settle instantly, so you can build without moving money.

Status

Track a transaction

Poll this for any collection or payout. It re-enquires the rail on read, so the status reflects reality in real time.

GET/v1/merchant/accounts/{accountId}/transactions/{txnId}/status
// PROCESSING → SUCCESS | FAILED   (proven live: HighTouch K1 Airtel collection)
{ "id": "9893373a-…", "status": "SUCCESS", "charge": "3", "net_amount": "100" }
Payouts

Disburse — with maker-checker

Paying money out is two-person by design (SEC-Z4). An initiator requests the payout; a different admin approves it before a single ngwee moves. No one can approve their own request.

Initiator requests →parked PENDING_APPROVAL →different admin Approver releases →dispatch SUCCESS
POST/v1/merchant/accounts/{accountId}/disburseADMIN / INITIATOR
Request — parks a payout
{
  "processor": "AIRTEL",
  "amount": "100",
  "msisdn": "260970000001",
  "reference": "payout-2001"
}
Response · 200 — no funds moved yet
{
  "id": "2b970dd7-…",
  "status": "PENDING_APPROVAL"
}
GET/v1/merchant/payout-requests?status=pendingthe approval queue
POST/v1/merchant/payout-requests/{id}/approveADMIN / APPROVER · ≠ requester
// creates + dispatches the disbursement; returns the transaction
{ "id": "ec86caf9-…", "type": "DISBURSEMENT", "status": "PROCESSING" }
POST/v1/merchant/payout-requests/{id}/rejectbody { "reason" }
POST/v1/merchant/payout-requests/{id}/cancelthe initiator withdraws their own request
🛡️

Approving blocks unless the rail can actually dispatch — if a processor is offline, approval is refused and no float is debited, so a payout can never get stuck half-sent. Manage who can initiate vs. approve under User Management (roles: Admin, Initiator, Approver, Viewer).
